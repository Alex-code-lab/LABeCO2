===============================================================================
PLAN DE MIGRATION HDF5 → SQLITE — LABeCO2
===============================================================================
Objectif : remplacer les fichiers HDF5 par une base SQLite relationnelle avec
IDs stables, liens explicites entre tables, statuts, sources et contributeurs.

Principe directeur : ne pas toucher l'interface avant d'avoir stabilisé le
modèle et validé que les calculs donnent les mêmes résultats qu'aujourd'hui.

===============================================================================
POURQUOI CETTE MIGRATION EST NÉCESSAIRE
===============================================================================

1. Les liens entre données reposent sur des noms texte, pas des IDs
-------------------------------------------------------------------------------
Aujourd'hui, un produit commercial liquide stocke dans sa colonne
"Facteur liquide source" le nom du facteur, par exemple "Acétone".
Le calculateur cherche ensuite ce nom dans la table des liquides.

Ce lien par texte est cassable à tout moment :
  - Quelqu'un corrige l'orthographe du facteur dans la table liquides.
  - Quelqu'un ajoute un accent ou modifie la casse.
  - Quelqu'un renomme le facteur pour être plus précis.
  → Le produit commercial ne trouve plus son facteur. Il tombe silencieusement
    dans le chemin "pas de facteur" et ses émissions massiques passent à 0.
    Aucune erreur n'est levée. Le calcul carbone est faux sans avertissement.

Avec des IDs stables, renommer un facteur ne casse rien. Le lien reste valide
parce qu'il pointe vers un identifiant numérique, pas vers un nom.

2. Il est impossible de détecter les doublons ou les incohérences à l'ajout
-------------------------------------------------------------------------------
HDF5 est un format de tableau, sans contraintes d'intégrité.
On peut aujourd'hui :
  - Ajouter deux fois le même facteur avec des valeurs CO2 différentes.
  - Ajouter un produit liquide sans facteur associé.
  - Ajouter un facteur sans source documentée.
  - Ajouter un matériau avec un nom légèrement différent de l'existant
    ("Polypropylène" vs "polypropylene") → deux entrées distinctes, résultats
    divergents selon laquelle est trouvée en premier.

Rien dans l'architecture actuelle ne l'empêche ni ne le signale à l'utilisateur.
Au fil des contributions, la base accumule des doublons et des données orphelines
dont on ne sait plus si elles sont valides ou abandonnées.

3. Il n'y a pas de traçabilité des ajouts
-------------------------------------------------------------------------------
Quand une valeur CO2 est questionnable, il est impossible de savoir :
  - Qui l'a ajoutée.
  - Quelle source justifie ce chiffre.
  - Si elle a été vérifiée ou si c'est une estimation provisoire.

Sans statut (draft / validated / deprecated) et sans lien vers une source et
un contributeur, toutes les valeurs sont traitées comme également fiables par
le calculateur. Une mauvaise valeur ajoutée par erreur a le même poids qu'une
valeur validée depuis une publication scientifique.

4. Le format HDF5 n'est pas adapté à une base collaborative
-------------------------------------------------------------------------------
HDF5 est conçu pour stocker efficacement de grands tableaux numériques.
Il n'est pas prévu pour :
  - Des relations entre tables (clés étrangères).
  - Des contraintes d'unicité ou de validité.
  - Un accès concurrent (plusieurs personnes qui écrivent en même temps).
  - Un historique des modifications.
  - Un système de révision ou d'approbation.

SQLite, à l'inverse, gère nativement les clés étrangères, les contraintes
UNIQUE et NOT NULL, et les transactions. Il reste un fichier local simple
(pas de serveur), mais avec les garanties d'une vraie base relationnelle.

5. Chaque ajout manuel aujourd'hui est un vecteur de bug silencieux
-------------------------------------------------------------------------------
Concrètement, quand un utilisateur ajoute un nouveau produit commercial
liquide via l'interface actuelle, il doit :
  - Taper manuellement le nom du facteur liquide dans un champ texte.
  - Ce nom doit correspondre exactement à ce qui existe dans la table liquides.
  - S'il fait une faute, le produit sera enregistré mais ses émissions seront
    calculées à 0 sans message d'erreur bloquant.

Avec SQLite et des IDs, l'interface proposera une liste déroulante des facteurs
existants. L'utilisateur choisit un facteur par son nom, mais c'est l'ID qui
est stocké. Il devient impossible de créer un lien cassé.

===============================================================================
PHASE 2 — DÉFINIR LE SCHÉMA SQLITE
===============================================================================
But : concevoir un schéma minimal mais complet, avec contribution et statut
dès le départ pour ne pas avoir à modifier les tables ensuite.

Règle : les IDs doivent être stables entre bases locales différentes.
Ne pas utiliser uniquement des INTEGER auto-incrémentés pour les tables métier :
deux contributeurs pourraient créer chacun un id = 42 dans deux bases locales.
Les IDs métier sont donc des UUID stockés en TEXT, générés par l'application.

-------------------------------
CONVENTIONS TRANSVERSALES
-------------------------------
  - Activer les contraintes : PRAGMA foreign_keys = ON.
  - Normalisation des noms (anti-doublon) :
    Les tables dont le nom doit être unique utilisent deux colonnes :
        name        TEXT NOT NULL          -- forme affichée ("Acétone")
        name_key    TEXT NOT NULL UNIQUE   -- forme normalisée ("acetone")
    name_key est généré par l'application à chaque insertion/modification :
        unicodedata.normalize("NFKD", name) → suppression des diacritiques → .lower().strip()
    La contrainte UNIQUE porte sur name_key, pas sur name.
    Tables concernées : emission_factors, materials.
    Tables non concernées : sources, contributors, commercial_products
    (plusieurs entrées peuvent avoir le même nom pour des raisons légitimes).
  - Toutes les tables métier utilisent :
        id              TEXT PRIMARY KEY       -- UUID stable global
        created_at      TEXT
        updated_at      TEXT
        status          TEXT NOT NULL DEFAULT 'draft'
                        -- draft / validated / deprecated
        contribution_id TEXT
        revision_of_id  TEXT
        validated_by_id TEXT REFERENCES contributors(id)
        validated_at    TEXT
        deprecated_at   TEXT
  - Les clés étrangères vers les tables métier sont en TEXT.
  - HDF5 reste importable, mais SQLite devient la source canonique.
  - L'Excel devient une vue lisible générée depuis SQLite, pas la source.

-------------------------------
TABLE : schema_migrations
-------------------------------
  version         INTEGER PRIMARY KEY
  name            TEXT NOT NULL
  applied_at      TEXT NOT NULL
  checksum        TEXT

-------------------------------
TABLE : contributors
-------------------------------
  id              TEXT PRIMARY KEY
  name            TEXT NOT NULL
  team            TEXT
  lab             TEXT
  email           TEXT    -- optionnel
  created_at      TEXT
  updated_at      TEXT

-------------------------------
TABLE : sources
-------------------------------
  id              TEXT PRIMARY KEY
  title           TEXT NOT NULL
  url             TEXT
  doi             TEXT
  citation        TEXT
  source_type     TEXT    -- article / rapport / mesure / catalogue / autre
  contributor_id  TEXT REFERENCES contributors(id)
  created_at      TEXT
  updated_at      TEXT
  status          TEXT NOT NULL DEFAULT 'draft'
  contribution_id TEXT
  revision_of_id  TEXT REFERENCES sources(id)
  validated_by_id TEXT REFERENCES contributors(id)
  validated_at    TEXT
  deprecated_at   TEXT

-------------------------------
TABLE : nacres_codes
-------------------------------
  id              TEXT PRIMARY KEY
  code            TEXT NOT NULL UNIQUE
  label           TEXT
  parent_code     TEXT

-------------------------------
TABLE : emission_factors
-------------------------------
  id              TEXT PRIMARY KEY
  name            TEXT NOT NULL
  name_key        TEXT NOT NULL UNIQUE   -- normalisé : sans accent, minuscule
  factor_type     TEXT    -- material / liquid
  co2_factor      REAL
  co2_unit        TEXT    -- kg CO2e/kg ou kg CO2e/L
  uncertainty     REAL
  density_g_ml    REAL    -- liquides uniquement
  concentration_mg_ml REAL
  source_id       TEXT REFERENCES sources(id)
  contributor_id  TEXT REFERENCES contributors(id)
  created_at      TEXT
  updated_at      TEXT
  status          TEXT NOT NULL DEFAULT 'draft'
  contribution_id TEXT
  revision_of_id  TEXT REFERENCES emission_factors(id)
  validated_by_id TEXT REFERENCES contributors(id)
  validated_at    TEXT
  deprecated_at   TEXT

-------------------------------
TABLE : materials
-------------------------------
  id              TEXT PRIMARY KEY
  name            TEXT NOT NULL
  name_key        TEXT NOT NULL UNIQUE   -- normalisé : sans accent, minuscule
  emission_factor_id TEXT REFERENCES emission_factors(id)
  source_id       TEXT REFERENCES sources(id)
  contributor_id  TEXT REFERENCES contributors(id)
  created_at      TEXT
  updated_at      TEXT
  status          TEXT NOT NULL DEFAULT 'draft'
  contribution_id TEXT
  revision_of_id  TEXT REFERENCES materials(id)
  validated_by_id TEXT REFERENCES contributors(id)
  validated_at    TEXT
  deprecated_at   TEXT

-------------------------------
TABLE : commercial_products
-------------------------------
  id              TEXT PRIMARY KEY
  name            TEXT NOT NULL
  brand           TEXT
  reference       TEXT
  code_nacres     TEXT
  product_type    TEXT NOT NULL
                  -- solid / liquid
  sold_packaging_label   TEXT
  units_per_sold_packaging INTEGER
  price_sold_packaging   REAL
  sold_unit_volume_ml    REAL
                  -- volume vendu par unité pour les vrais produits liquides
  capacity_volume_ml REAL
                  -- capacité informative d'un objet solide (boîte 300 mL,
                  -- sac 10 L, tube 2 mL). Ne déclenche pas un calcul liquide.
  emission_factor_id  TEXT REFERENCES emission_factors(id)
                      -- obligatoire uniquement si product_type = liquid
  ijm_catalogue_id    TEXT REFERENCES catalogue_ijm(id)
  source_id           TEXT REFERENCES sources(id)
  contributor_id      TEXT REFERENCES contributors(id)
  created_at          TEXT
  updated_at          TEXT
  status              TEXT NOT NULL DEFAULT 'draft'
  contribution_id     TEXT
  revision_of_id      TEXT REFERENCES commercial_products(id)
  validated_by_id     TEXT REFERENCES contributors(id)
  validated_at        TEXT
  deprecated_at       TEXT

-------------------------------
TABLE : product_components
-------------------------------
  id              TEXT PRIMARY KEY
  product_id      TEXT NOT NULL REFERENCES commercial_products(id)
  component_type  TEXT NOT NULL
                  -- product / primary_packaging / secondary_packaging
  material_id     TEXT REFERENCES materials(id)
  mass_g          REAL
  units_divisor   INTEGER DEFAULT 1
                  -- ex : conditionnement primaire divisé par unités vendues

-------------------------------
TABLE : catalogue_ijm
-------------------------------
  id              TEXT PRIMARY KEY
  code_ijm        TEXT
  designation     TEXT
  brand           TEXT
  conditionnement TEXT
  price_ht        REAL
  units_per_pack  INTEGER
  source_catalogue TEXT
  imported_at     TEXT

-------------------------------
TABLE : transport_factors
-------------------------------
  id              TEXT PRIMARY KEY
  origin          TEXT NOT NULL
  distance_km     REAL
  mode            TEXT
  factor_kgco2e_per_kg REAL NOT NULL
  uncertainty     REAL
  source_id       TEXT REFERENCES sources(id)
  contributor_id  TEXT REFERENCES contributors(id)
  created_at      TEXT
  updated_at      TEXT
  status          TEXT NOT NULL DEFAULT 'draft'
  contribution_id TEXT
  revision_of_id  TEXT REFERENCES transport_factors(id)
  validated_by_id TEXT REFERENCES contributors(id)
  validated_at    TEXT
  deprecated_at   TEXT

Remarques :
  - Un produit commercial liquide pointe vers emission_factor_id (l'ID du
    facteur liquide), pas vers un nom texte comme "Acétone".
  - Un matériau solide pointe également vers emission_factor_id.
  - Les masses et matériaux multiples d'un produit ne sont plus des colonnes
    material_1/material_2/material_3 : ils sont stockés dans product_components.
  - Le transport a sa table dédiée, car il dépend d'une origine, d'une distance
    et d'un mode, pas seulement d'un facteur CO2 générique.
  - Les codes NACRES sont stockés dans nacres_codes pour éviter les libellés
    divergents et faciliter les listes déroulantes.
  - source et contributor sont toujours deux champs séparés.
  - product_type distingue le produit acheté, pas seulement l'unité :
      * liquid = vrai liquide/réactif/solvant acheté.
      * solid = objet solide, même si son libellé contient une capacité en mL/L
        (boîte 300 mL, sac 10 L, tube 2 mL, flacon vide).
    Le volume d'un solvant vendu et la capacité d'un objet solide doivent être
    stockés dans deux champs différents.

===============================================================================
PHASE 3 — ÉCRIRE LE SCRIPT DE MIGRATION HDF5 → SQLITE
===============================================================================
But : créer tools/migrate_hdf5_to_sqlite.py.
On ne modifie pas encore l'app. Ce script lit les HDF5 et produit un SQLite.

Étapes du script :
  0. Créer le schéma SQLite, insérer la version dans schema_migrations,
     activer PRAGMA foreign_keys = ON, et générer des UUID pour chaque ligne.
     Générer name_key pour emission_factors et materials via la fonction normalize()
     (NFKD → suppression diacritiques → lower → strip).
  1. Lire data_eCO2_liquides_consommable → créer les emission_factors (liquides).
  2. Lire empreinte_carbone_materiaux → créer les materials + emission_factors
     (matériaux).
  3. Lire data_eCO2_masse_consommable → créer les commercial_products.
     - Pour chaque produit : résoudre "Facteur liquide source" → emission_factor_id.
     - Classer product_type :
         * liquid si un facteur liquide source est présent, ou si le code/libellé
           indique clairement un réactif, solvant, milieu ou solution liquide.
         * solid si le volume correspond seulement à une capacité d'objet
           (boîte, sac, tube, étiquette, flacon vide, etc.).
       Dans ce deuxième cas, migrer le volume vers capacity_volume_ml, pas vers
       sold_unit_volume_ml.
     - Pour chaque masse/matériau : créer une ligne product_components.
     - Pour chaque emballage secondaire ou conditionnement primaire :
       créer une ligne product_components avec component_type explicite.
  4. Lire les codes NACRES présents → créer nacres_codes.
  5. Lire les facteurs transport → créer transport_factors.
  6. Lire le catalogue IJM → créer les catalogue_ijm + lier aux produits.
  7. Créer une source générique "HDF5 import" et un contributeur "migration".

Rapport de migration (affiché et enregistré en migration_report.txt) :
  - Produits solides migrés : N
  - Produits liquides commerciaux migrés : N
  - Facteurs liquides migrés : N
  - Facteurs matériaux migrés : N
  - Produits liquides reliés à un facteur : N
  - Produits liquides sans facteur trouvé : N  (→ listés nominativement)
  - Composants produits créés : N
  - Composants incomplets : N                  (→ listés)
  - Matériaux d'emballage non résolus : N      (→ listés)
  - Doublons suspects (même nom + code_nacres) : N (→ listés)
  - Codes NACRES importés : N
  - Facteurs transport importés : N
  - Entrées catalogue IJM importées : N
  - Liens non résolus : N                      (→ listés)

Validation après migration :
  - Reprendre les fixtures de la Phase 1b.
  - Rejouer les mêmes calculs avec le DataManager SQLite (Phase 4).
  - Comparer les résultats carbone et prix : écart toléré < 0,01 %.

PHASE 4 — CRÉER UNE COUCHE DATAMANAGER COMPATIBLE SQLite
===============================================================================
But : remplacer la lecture HDF5 par SQLite sans casser main_window.py ni
carbon_calculator.py.

Structure des nouveaux fichiers :
  ui/db_connection.py     → connexion SQLite + helpers de requête
  ui/repositories.py      → une classe par table (ProductRepository,
                             FactorRepository, MaterialRepository, …)

Interface explicite (à définir d'abord) :
  Créer une classe abstraite ou un protocole Python (typing.Protocol) qui
  liste toutes les méthodes exposées par DataManager :
    get_liquid_data(code_nacres, produit) → Series | None
    get_material_data(name) → (float, float) | (None, None)
    get_prix_unitaire_info(code_nacres, consommable) → dict | None
    get_consumable_liquid_factor_data(code_nacres, consommable) → (Series, Series)
    get_main_data() → DataFrame
    get_data_masse() → DataFrame
    get_transport_factor(origine) → (float, float)
    is_liquid_commercial_row(row) → bool
    nacres_code_mask(series, code) → BooleanSeries

DataManager hérite de cette interface ET reste l'implémentation HDF5.
DataManagerSQLite hérite de la même interface, lit SQLite.

Pendant la transition, un flag de configuration choisit l'implémentation.
Après validation, DataManager HDF5 est déprécié mais conservé pour import
d'anciens fichiers.

Critère de réussite :
  Tous les tests existants (159 tests) passent sans modification.
  Coverage est disponible pour mesurer la couverture, sans seuil global imposé
  au départ car l'application est encore très UI-heavy.
  Les fixtures de Phase 1b donnent des résultats identiques avec les deux
  implémentations.

PHASE 6 — ADAPTER LA FENÊTRE CONSOMMABLES / FACTEURS
===============================================================================
But : permettre l'ajout et la modification de données via l'interface,
en stockant des IDs et non des noms.

Pour l'ajout d'un produit commercial :
  - Choisir solide ou liquide.
  - Renseigner nom, marque, référence, code NACRES.
  - Pour liquide : choisir un facteur existant via menu déroulant (ID stocké).
  - Ou créer un nouveau facteur (ouvre le formulaire facteur, retourne l'ID).
  - Pour solide : créer les product_components depuis les matériaux choisis
    (produit, conditionnement primaire, emballage secondaire).
  - Pour solide avec capacité (boîte 300 mL, tube 2 mL, sac 10 L) :
    renseigner capacity_volume_ml facultatif, sans rendre le facteur liquide
    obligatoire.
  - Source et contributeur : champs obligatoires.
  - Statut initial : draft.

Pour l'ajout d'un facteur :
  - Choisir le type : matériau solide ou facteur liquide/solvant.
  - Renseigner nom, CO2, incertitude, unité.
  - Pour liquide : renseigner densité, concentration, unité de volume.
  - Source obligatoire (sélection dans la liste ou création).
  - Contributeur obligatoire.
  - Statut initial : draft.

===============================================================================
PHASE 7 — METTRE EN PLACE LE SYSTÈME DE CONTRIBUTION
===============================================================================
But : permettre à plusieurs personnes d'ajouter des données sans modifier
directement la base validée.

Workflow :
  1. L'utilisateur ajoute une donnée → statut = draft dans sa base locale.
  2. Il exporte sa contribution :
       contribution_LABeCO2_YYYY-MM-DD_[nom].json
     Le JSON est le format principal car il est lisible en revue humaine.
     SQLite reste un format optionnel pour gros lots ou outils automatisés.
  3. Un mainteneur importe, vérifie, valide ou rejette chaque entrée.
  4. Les entrées validées passent en statut = validated dans la base officielle.

Règles :
  - Une entrée validated ne peut pas être modifiée sans créer une nouvelle
    révision (nouvelle ligne avec statut draft, revision_of_id vers l'ancienne).
  - Une entrée deprecated reste en base pour l'historique.
  - Le JSON de contribution contient les UUID, les champs métier, les sources,
    les contributeurs et les dépendances nécessaires.

Outils à créer :
  tools/export_contribution.py   → exporte les draft de l'utilisateur
  tools/import_contribution.py   → importe, vérifie les UUID, et affiche un diff
                                  lisible avant validation

===============================================================================
PHASE 9 — VALIDATION QUALITÉ AUTOMATIQUE
===============================================================================
But : détecter les incohérences avant qu'elles n'atteignent les calculs.

Contrôles à implémenter (peuvent tourner à l'import ou à la demande) :
  - Produit liquide sans emission_factor_id → erreur bloquante.
  - Produit solide avec capacity_volume_ml mais sans emission_factor_id → OK
    (la capacité n'est pas un facteur liquide).
  - Facteur sans source → erreur bloquante.
  - Source sans contributeur → erreur bloquante.
  - Prix négatif → erreur bloquante.
  - Prix absent → avertissement, sauf si le calcul demandé dépend du prix.
  - Volume liquide vendu absent sur produit liquide → erreur bloquante.
  - Doublon probable (même nom + code_nacres) → avertissement.
  - Facteur CO2 aberrant (< 0 ou > 100 kg CO2e/kg) → avertissement.
  - Densité liquide hors plage (< 0.5 ou > 2.0 g/mL) → avertissement.
  - Entrée validated modifiée sans révision → erreur bloquante.

Tests à ajouter pour cette phase :
  - Création du schéma SQLite avec PRAGMA foreign_keys = ON.
  - Présence de schema_migrations.
  - UUID uniques sur toutes les tables métier.
  - Migration HDF5 vers product_components.
  - Résolution "Facteur liquide source" → emission_factor_id.
  - Migration transport vers transport_factors.
  - Export contribution JSON lisible.
  - Règles qualité : prix négatif bloquant, prix absent avertissement,
    liquide sans facteur bloquant.
