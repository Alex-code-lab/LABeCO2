## Plan de refactorisation — Moteur qualité commun

### Objectif

Créer une source unique pour les règles qualité utilisées par :

- tools/admin/workflow.py : validation d'une entrée ou d'une sélection avant
  changement de statut.
- ui/quality_check.py : audit global de la base.
- ui/validate_window.py : affichage des erreurs, avertissements et détails pour
  prendre une décision de validation.

La règle centrale doit être : une règle qualité est définie une seule fois, puis
appelée par les différents écrans selon leur contexte. Les interfaces peuvent
filtrer ou présenter les résultats différemment, mais ne doivent pas réécrire la
logique métier.

### Principe de migration

La migration doit être progressive et sans changement de comportement au début.

1. Ajouter des tests de parité sur les règles déjà connues.
   - Même produit liquide sans facteur : WARNING dans workflow.py et
     quality_check.py.
   - Même code NACRES à ne plus utiliser : WARNING dans les deux chemins.
   - Même produit sans conditionnement : WARNING dans les deux chemins.
   - Même produit sans nom, référence ou NACRES valide : ERROR quand la règle est
     bloquante.

2. Créer un module métier sans dépendance Qt.
   - Chemin proposé : tools/admin/quality_rules.py.
   - Ce module ne doit importer ni PySide/PyQt, ni widgets, ni logique
     d'affichage.
   - Il doit contenir les dataclasses communes :
     QualityIssue, QualityContext, QualityRuleResult si utile.

3. Stabiliser le format unique d'une anomalie qualité.
   Champs minimaux :
   - severity : ERROR, WARNING ou INFO.
   - table : table concernée.
   - row_id : identifiant de l'entrée concernée.
   - rule : identifiant stable de la règle.
   - message : libellé français affichable.
   - value : valeur utile au diagnostic, optionnelle.
   - aux_id : identifiant secondaire, par exemple product_components.id.
   - blocking : booléen calculé depuis severity ou explicitement porté par la
     règle si nécessaire.

4. Extraire d'abord les règles ligne par ligne.
   Priorité :
   - commercial_products : nom, référence, NACRES, statut, type produit,
     conditionnement, liquide sans facteur, NACRES 2026 sans FE.
   - materials : nom, facteur CO2, source.
   - emission_factors : source, incertitude, valeur hors plage.
   - sources et contributors : champs minimaux.

5. Extraire ensuite les règles transverses base entière.
   Ces règles ont besoin de requêtes globales :
   - doublons métier produits.
   - composants pointant vers produit absent.
   - composants pointant vers matériau absent.
   - facteurs ou matériaux sans source.
   - cohérence entre produit liquide et facteur liquide disponible.

6. Transformer workflow.py en adaptateur.
   - workflow.py garde les transitions pending/draft/validated/deprecated.
   - Avant une transition, il appelle tools/admin/quality_rules.py.
   - Il ne porte plus les règles elles-mêmes, seulement la politique :
     ERROR bloque, WARNING informe, INFO trace.

7. Transformer quality_check.py en adaptateur d'audit global.
   - quality_check.py construit le contexte SQLite.
   - Il appelle le moteur commun.
   - Il garde uniquement les fonctions utiles à l'UI qualité :
     tri, regroupement, texte de synthèse, actions de correction.

8. Nettoyer validate_window.py.
   - validate_window.py ne décide pas des règles.
   - Il affiche les colonnes, détails, avertissements et erreurs fournis par le
     moteur.
   - Les boutons "Valider", "Rejeter", "Contrôle qualité sélection" utilisent
     les mêmes résultats qualité.

### Politique de sévérité à conserver

- ERROR : bloque une validation.
- WARNING : visible, explicite, mais non bloquant.
- INFO : contexte ou dette de qualité non urgente.

Règles importantes :

- Code NACRES sans FE Labo1point5 : WARNING, jamais bloquant.
- Code NACRES à ne plus utiliser : WARNING, non bloquant tant qu'on conserve
  l'historique.
- Produit liquide sans facteur liquide : WARNING tant que le calcul prix/NACRES
  reste disponible, ERROR seulement si l'usage nécessite explicitement un calcul
  masse/volume.
- Produit sans conditionnement : WARNING si une autre information de contexte
  existe, ERROR uniquement si le conditionnement est indispensable à l'opération
  demandée.
- Produit sans nom, sans référence ou sans code NACRES valide : ERROR pour une
  validation stable.

### Tests à ajouter avant et pendant le refactor

- Tests unitaires du moteur commun :
  - chaque règle retourne le même rule id, message et severity.
  - chaque règle distingue correctement ERROR/WARNING/INFO.
  - aucun test ne dépend de Qt.

- Tests de parité :
  - un même produit testé par workflow.py et quality_check.py retourne les mêmes
    rules.
  - un même cas limite ne peut pas être bloquant dans un chemin et non bloquant
    dans l'autre.

- Tests SQLite intégration :
  - audit global sur base fixture.
  - validation d'une sélection avec erreurs bloquantes.
  - validation d'une sélection avec warnings seulement.
  - correction d'un composant orphelin via aux_id.

- Tests UI smoke :
  - ouverture rapide de lab_admin.
  - contrôle qualité sélection sans freeze.
  - validation groupée avec warnings non bloquants.
  - rejet groupé sans rechargement complet.

### Ordre recommandé d'implémentation

1. Ajouter tests de parité sur les règles actuelles avant tout déplacement.
2. Créer tools/admin/quality_rules.py avec QualityIssue commun.
3. Déplacer les règles commercial_products simples.
4. Brancher workflow.py sur le moteur commun.
5. Brancher quality_check.py sur le moteur commun.
6. Déplacer les règles transverses base entière.
7. Supprimer les duplications restantes.
8. Lancer l'audit réel et comparer les compteurs avant/après.
9. Ajuster uniquement les différences attendues et les documenter dans cet
   audit.

### Critères d'acceptation

- pytest -q passe.
- Les compteurs d'audit global restent identiques, sauf changements explicitement
  documentés.
- Une règle modifiée dans le moteur commun change workflow.py et quality_check.py
  en même temps.
- Aucun ERROR n'est introduit à la place d'un WARNING sans décision explicite.
- Les nouveaux codes NACRES 2026 sans FE restent visibles en orange/avertissement
  mais ne bloquent pas la validation.
- lab_admin reste réactif sur validation, rejet, recherche catalogue et audit
  global.
